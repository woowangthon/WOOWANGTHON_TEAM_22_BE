1. 이번에 해결한 범위

기존 ComicAIClient, 이미지 정규화, comic_previews/첨부, persist_result와
recover_result_uploads를 재사용한다. 새 인프라는 없다.
ComicJobService는 단일 BE 앱 lifespan에서 asyncio task 하나로 순차 실행한다.
이 task 자체가 영속 큐라는 뜻은 아니다. 작업/원문/확인 plan/전송 상태는 DB에 있다.
서버 종료·절전 중 실행하지 않는다. 다음 정상 기동 후 DB를 스캔해 재개한다.

새 작업 테이블 하나: comic_generation_jobs.
- 회원, session, draft, revision, 원래 client_request_id, 원문, confirmed_plan,
  확인값을 포함한 요청 fingerprint, preview_id, 컷별 상태·자산 ID/해시,
  claim_token, lease_until, 결과 저장 여부를 기록한다.
- fingerprint는 input_confirmed=true/scene_confirmed=true와 전체 확인 plan에 결합된다.
  HTTP에서 두 확인값과 서버 초안/원문/출처/순서를 검증한 뒤에만 admit한다.
  원문 snapshot은 생성/결과 저장 복구용이다. 기존 전체 대화 세션 영속화를 대체하지 않는다.
- 회원+session+request_id 고유 제약과 회원+session+draft+revision 고유 제약.
  같은 키/같은 본문은 같은 작업. 같은 키 다른 본문은409 IDEMPOTENCY_CONFLICT.
  같은 초안을 새 키로 우회하면409 COMIC_DRAFT_ALREADY_REQUESTED.
- DB FOR UPDATE SKIP LOCKED + claim_token + 300초 lease로 한 담당자만 claim.
  worker는 각 단계 전에 token/lease를 검사하는 RPC를 사용한다.
  재claim은 lease 만료 후에만 가능하고 dispatched를 waiting으로 되돌리지 않는다.
- 현재 BE는 단일 worker로 구성했지만 두 앱이 같은 DB를 사용하는 경쟁도 Fake에서 검증했다.
  실제 PostgreSQL 다중 연결 잠금/RLS/rollback은 미검증이다.

2. 컷별 실행·바이트 보관·복구

waiting → dispatched(DB에 먼저 기록) → AI 호출 1회 → PNG 정규화
→ checkpoint(자산 ID/해시 DB 기록) → private Storage 업로드 → ready(DB 기록).
ready를 기록한 다음에 다음 원본 컷으로 진행한다. 반복 컷은 원본 컷 자산만 재사용한다.

- 기존 diary-private/{user_uuid}/{preview_uuid}/comic_scene/{asset_uuid}.png.
  기존 버킷·정책·원본 그림은 변경하지 않는다. upsert=false와 충돌 해시 확인을 재사용한다.
- 업로드/DB 응답 유실 때 마지막 생성 이미지 한 개(정규화 최대10MiB)를 실행기 메모리에
  보존한다. 다음 순회는 DB 상태부터 읽고 같은 바이트 업로드·완료만 복구한다.
- 재시작 때 checkpoint가 있으면 기존 Storage 객체를 읽어 크기·해시와 디코딩 메타데이터를
  확인한다. 업로드 응답만 유실된 경우 기존 객체로 복구한다. 새 이미지를 생성하지 않는다.
- dispatched 상태인데 바이트/체크포인트가 없으면 unknown. checkpoint가 있지만
  프로세스 메모리가 소실되고 Storage도404이면 unknown이다. 이미 기록한 자산 ID/해시는 남긴다.
  Storage의503/권한/timeout/해시 불일치는404처럼 유실 확정하지 않고 확인 실패로 보존한다.
- ready 컷은 재생성하지 않는다. 공급자502/503/504/timeout/손상 응답도 재호출하지 않는다.
  unknown 발생 뒤 아직 시작하지 않은 컷도 unknown으로 남겨 추가 비용 실행을 중단한다.
  failed/rejected/mock으로 명확히 응답된 컷은 성공 이미지로 바꾸지 않는다.
- 전송 기록 후 실제 HTTP 전송 전 죽은 경우에도 보수적으로 unknown이다.
  공급자가 완료했지만 응답을 잃은 경우 실제 생성 여부는 자동으로 알아낼 수 없다.
- 최종 결과는 보관된 컷으로 기존 persist_result(upload=False, DB 승인 원문 snapshot)를 호출해
  immutable 결과를 저장한 후 recover_result_uploads(saved=검증된 결과)로 완료한다.
  기존 함수들의 기본 호출 방식/검증/첨부 계약은 유지한다. 위 옵션은 HTTP 입력이 아니다.
  Storage 바이트를 다시 읽고 최종 저장할 때 유료 생성은 없다.
- 모든 결과가 기록된 뒤 complete RPC가 실제 comic_previews의 owner/초안/본문/패널을
  다시 대조하고 result_saved=true를 설정한다. unknown 패널이 있으면 job_state=unknown,
  그 외에는 job_state=completed. completed라도 이미지 모두 failed일 수 있으므로 status도 본다.
- unknown은 자동 재claim/재생성하지 않는다. 운영자가 원장이나 Storage를 임의로 초기화해
  재생성하는 도구도 제공하지 않는다. 생성 전후 유실 구간에서 exactly-once 성공을 보장하지 않는다.
  목표는 동일 컷의 자동 유료 재실행 방지와 이미 보관한 성공 컷의 재사용이다.

3. 활성화와 시간 예산

app.main의 기본 app=create_app()는 enable_comic_worker=False이다.
활성화 환경변수를 만들지 않았다. 운영 생성 POST는 기존503을 유지한다.
로컬 검증에서만 create_app(..., enable_comic_worker=True)를 명시한다.
이 옵션만으로 무조건202가 되지 않는다:
- Storage writer 설정, 작업 스키마 probe(version1/기존 결과 함수), 살아 있는 worker task가 필요.
- 영속 admit 성공 뒤에도 실행 담당자 상태를 확인한다. 없거나 DB 준비 실패이면503.
- DB admit가 완료됐지만 응답을 잃을 수 있으므로503 COMIC_JOBS_UNAVAILABLE은
  미접수 증거가 아니다. 원래 request_id GET으로만 확인한다.
- worker 중단/오류를 health200에 숨겨 생성 성공으로 처리하지 않는다.
  기본 /health는 기존 그림일기 서비스의 생존 확인이며 만화 readiness와 다르다.

POST는 네 컷을 기다리지 않고 영속 접수 상태를 반환한다.
worker 전용 AI HTTP는 connect3/read200/write10/pool3초, 전체 호출210초, 자동 재시도0.
AI 컷별180초와 별도로 여유를 두고 각 단계 lease300초를 사용한다.
기존 대화/초안 HTTP130/135초·FE AI150초는 변경하지 않았다.
네 컷 전체가150초를 넘더라도 POST를 붙잡지 않는다. FE는 GET을 사용한다.
실제 AI 품질/최대 지연·SDK deadline 엄수·Render 절전/Linux shutdown은 미검증이다.
중단된 작업의 재claim까지 최장 약300초가 필요할 수 있다. 시연에서 반드시 고려한다.

4. FE 정확한 요청·응답 계약

기존 원문 확인 POST .../comic-plans와 생성 요청 본문은 직전 연결 패치와 동일하다.
POST /api/chat-sessions/{session_id}/comic-previews
Authorization: Bearer <회원 토큰>
{
  "client_request_id":"comic_original_key",
  "history_revision":1,
  "draft_id":"draft_...",
  "input_confirmed":true,
  "scene_confirmed":true,
  "confirmed_plan": <원문/장면 화면에서 확인한 기존 VisualPlan 전체>
}

정상 접수/같은 실행 중 요청: HTTP202. 완료된 같은 요청 재사용: HTTP200.
기본 운영 앱: HTTP503 COMIC_PREVIEW_NOT_ENABLED, retryable=false.
202의 status=queued/running은 실제 영속 기록과 worker 준비가 있을 때만 반환한다.
POST는 서명 URL을 만들지 않으며 FE는 후속 GET으로 이미지를 받는다.

신규 읽기 전용 복구:
GET /api/chat-sessions/{session_id}/comic-requests/{client_request_id}
Authorization: Bearer <회원 토큰>
추가 본문/쿼리/fingerprint/preview_id는 필요 없다. 원래 키를 보관해야 한다.
세션 메모리 소실 후에도 회원+session+원래키로 DB 기록을 읽는다.
타회원/잘못된 세션/미발견은 동일하게200 receipt_found=false/unknown이며 다른 회원 존재를 알리지 않는다.
DB 미설치/권한/연결 오류는503 COMIC_JOBS_UNAVAILABLE, 기록 형식 오류는502.
기존 인증 오류 외피/401과 요청 키 형식422는 그대로다.

공통 응답(기존 ComicResponse에 다음 필드를 추가):
{
  "client_request_id":"comic_original_key",
  "job_state":"queued | running | completed | unknown",
  "receipt_found":true,
  "worker_available":true,
  "retry_generation_allowed":false,
  "preview_id":"UUID 또는 null",
  "status":"none | queued | running | ready | partial | failed",
  "panels":[{"position":1,"caption":"원문 글","status":"pending | ready | failed | rejected | mock | unknown",
             "imageUrl":"서명 URL 또는 null","expires_at":"UTC ISO 시각 또는 null"}],
  "recovery_required":false,
  "error_code":null
}

- completed: 저장된 preview를 재조회해 반환. ready/partial/failed는 이미지 결과를 뜻한다.
- queued/running: DB 기록 상태. running은 유효 claim lease가 있는 상태이며 실행 완료 보장이 아니다.
  worker_available은 이 BE 프로세스의 실행 task 상태. false이면 실행 중이라고 안내하지 않는다.
- lease가 만료된 running은 GET에서 unknown/recovery_required=true로 보인다.
  GET이 DB 상태를 바꾸지는 않는다. 정상 worker가 다음 claim 때 안전한 컷만 복구한다.
- unknown: 원래 요청 유지. 부분 ready 패널과 error_code=COMIC_RESULT_UNKNOWN이 함께 올 수 있다.
  바이트 유실이 포함된 결과를 새 생성 허가로 바꾸지 않는다.
- 미발견: receipt_found=false, job_state=unknown, preview_id=null, status=none, panels=[],
  error_code=COMIC_RESULT_UNKNOWN. 요청이 실패했다는 확정이나 새 요청 ID 발급 허가가 아니다.
- retry_generation_allowed는 항상false. 자동 POST 재전송/새 키 생성 금지.
- GET은 DB SELECT와 기존 ready 이미지의 URL 서명만 수행한다. AI 생성·원장 RPC·업로드·
  상태 완료·첨부를 실행하지 않는다. URL 발급의 기존 Storage sign POST는 객체 쓰기가 아니다.
  실제 동작 중인 worker는 GET과 독립적으로 작업할 수 있다.

FE 적용할 순서:
1) 클릭 시 원래 request_id/session/draft/revision/확인 plan을 고정해 POST 한 번.
2) 202 또는 결과 불명/통신 오류: 원래 키의 신규 GET을 약1~2초 간격으로 조회.
   연속 오류는 대기/수동 확인으로 전환. 폴링 중 새 생성 POST 없음.
3) queued/running은 대기. completed 또는 unknown은 자동 생성/폴링을 멈추고 실제 패널 상태 표시.
   worker 불가/lease 만료 unknown은 '기존 작업 확인 필요'로 표시하고 새 키를 만들지 않는다.
4) 기본 그림일기 저장 버튼은 유지. 성공한 결과의 기존 POST diaries/{id}/comics 첨부는 별도 처리.
   기존 preview UUID GET/저장 만화 GET/첨부 JSON은 변경하지 않았다.
5) 직전 FE_COMIC_CONNECT.patch는 동기 성공 응답을 전제로 하므로 이 비동기 계약 반영이 필요하다.
   이번에 FE 원본이나 기존 패치를 덮어쓰지 않았다. 담당자에게 문서를 전달해야 한다.

3) 현 Render 소스에 새 실행기/worker 전용 시간 설정을 반영·기동 검증하지 않았고,
   절전·Linux 종료·메모리/동시 부하·실모델 지연과 품질은 미검증이다.
