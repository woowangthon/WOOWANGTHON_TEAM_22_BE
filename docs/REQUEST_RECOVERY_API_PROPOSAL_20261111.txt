3. 공통 규칙

Authorization: Bearer <Supabase 회원 access_token> 필수. GET 본문 없음.
client_request_id: 영문/숫자/_/- 1~128자. 응답 Cache-Control:no-store, X-Request-ID 유지.
회원 ID/역할/날짜는 FE가 지정하지 않는다. 기존 PUT/POST 요청·성공 응답은 변경하지 않았다.
복구 GET은 RPC, 업로드, 서명 URL 발급, 보상 지급, 수정 재시도, 물주기 재시도를 하지 않는다.

200 status=completed: 정확히 해당 요청의 완료 영수증을 확인했다.
200 status=unknown: 완료를 확인하지 못했다. 부재와 pending을 실패로 확정하지 않는다.
HTTP 오류/타임아웃/잘못된 응답: FE는 기존 unknown을 유지한다.
어떤 경우도 unknown에서 자동으로 새 ID/같은 ID PUT·POST를 실행하지 않는다.

PostgreSQL SELECT에 행이 없어도 예약 INSERT나 물주기 트랜잭션이 아직 커밋되지 않았을 수 있다.
여러 번 조회해도 비어 있다는 사실, 같은 edit_version, 날짜 변경, 경과 시간은
처리 중 요청이 없다는 증명이 아니다. 이번 API는 안전한 재전송 승인 기능을 제공하지 않는다.

4. A — 원래 일기 수정 요청 조회

GET /api/diaries/{diary_id}/edits/{client_request_id}
필수 query:
  fingerprint: 원래 PUT 입력의 SHA256 소문자 hex64 (계산법 아래)
  expected_version: 원래 PUT에 보낸 정수1~2147483646
다른 query 필드는422. fingerprint를 현재 상세의 글/그림/버전으로 재계산하지 않는다.

요청 예:
GET /api/diaries/aaaaaaaa-aaaa-4aaa-8aaa-aaaaaaaaaaaa/edits/edit-1?fingerprint=ab1b85594ee7b30d4a5bfef3ef87093284bf68a0e2e6dd25c30846221156dbd5&expected_version=1
Authorization: Bearer <member_access_token>

완료200:
{"diary_id":"aaaaaaaa-aaaa-4aaa-8aaa-aaaaaaaaaaaa","client_request_id":"edit-1","fingerprint":"ab1b85594ee7b30d4a5bfef3ef87093284bf68a0e2e6dd25c30846221156dbd5","expected_version":1,"status":"completed","edit_version":2}
결과 불명200:
{"diary_id":"aaaaaaaa-aaaa-4aaa-8aaa-aaaaaaaaaaaa","client_request_id":"edit-1","fingerprint":"ab1b85594ee7b30d4a5bfef3ef87093284bf68a0e2e6dd25c30846221156dbd5","expected_version":1,"status":"unknown","edit_version":null}

응답 diary_id/client_request_id/fingerprint/expected_version은 조회 대상 값이다.
unknown 응답의 fingerprint는 입력 echo이며 저장된 영수증이 있다는 뜻이 아니다.
completed에서는 영수증의 회원/키/일기/fingerprint/expected_version, state/result,
결과 버전=expected_version+1/본문/그림 ready 및 새 그림 영수증 동일성을 검증한다.
일치하는 영수증이 있어도 pending이면unknown. 다른 본문/파일/버전/일기로 같은 키를 조회하면409.

completed.edit_version은 당시 완료 버전이다. 현재 활성 버전/그림임을 보장하지 않는다.
나중에 다른 수정이 완료되었다면 현재 상세는 더 새 버전일 수 있다.
FE는 완료된 원래 요청을 정리한 뒤 상세 GET으로 현재 화면을 갱신하되, 원래 요청과
다른 화면/편집 세션에 늦은 조회 응답을 적용하지 않는다. 원래 글·Blob을 그 전까지 보존한다.
404도 과거 수정이 실패했다는 증거는 아니다. 삭제/접근 불가 UI와 결과 불명 보존을 구분한다.

fingerprint 계산은 기존 app/services/edits.py의 PUT 알고리즘과 동일하다:
SHA256(UTF8(JSON({client_request_id, confirmed_text, expected_version, file_sha256})))
- 키 순서는 위의 알파벳 순서로 고정. JSON 공백 없음, Unicode는 UTF8 그대로.
- expected_version은 JSON 숫자. 텍스트 trim/Unicode 정규화/줄바꿈 변환 없음.
- file_sha256은 실제 전송 Blob 원본 바이트의 SHA256 소문자 hex64, 파일 생략은null.
- 저장된 Drawing.sha256은 PNG 정규화 후 해시이므로 file_sha256 대신 쓸 수 없다.
- 실제 PUT 직전에 요청의 본문/버전/Blob을 고정하고 fingerprint를 계산해 보관한다.
  원래 Blob이 없어 fingerprint를 재구성할 수 없으면 조회 입력을 추측하지 않는다.

FE 연결 예시(원본 FE 파일에는 적용하지 않음):
async function sha256Hex(bytes) {
  const hash = await crypto.subtle.digest('SHA-256', bytes);
  return Array.from(new Uint8Array(hash), b => b.toString(16).padStart(2, '0')).join('');
}
async function editFingerprint(req) {
  const fileHash = req.blob == null ? null : await sha256Hex(await req.blob.arrayBuffer());
  const canonical = JSON.stringify({
    client_request_id: req.client_request_id,
    confirmed_text: req.confirmed_text,
    expected_version: req.expected_version,
    file_sha256: fileHash
  });
  return sha256Hex(new TextEncoder().encode(canonical));
}
const query = new URLSearchParams({fingerprint: savedFingerprint, expected_version: String(req.expected_version)});
// 기존 api helper로 GET. savedFingerprint는 원래 요청에서 저장해 둔 값.
const receipt = await api(`/api/diaries/${diaryId}/edits/${req.client_request_id}?${query}`);
// 모든 대상 식별값 일치 + status==='completed' 때만 원래 요청 완료 처리.

검산 벡터(파일 없음):
{"client_request_id":"edit-1","confirmed_text":"수정한 일기","expected_version":1,"file_sha256":null}
→ ab1b85594ee7b30d4a5bfef3ef87093284bf68a0e2e6dd25c30846221156dbd5
이 fingerprint는 인증 토큰/비밀키가 아니며 회원 인증과 소유권 검사를 대체하지 않는다.
