# 그림일기 비공개 Storage 초안

2026-11-07 기준 미적용 제안이다. 실제 버킷 생성·파일 업로드·SQL 실행은 하지 않는다.
[DB 초안](DIARY_DB_SCHEMA.md)과 `20261107000200_private_diary_storage_policies.sql`을 함께 검토한다.

## 버킷 준비 — Dashboard 또는 Storage API로 별도 수행

| 항목 | 후보 설정 |
| --- | --- |
| 버킷 ID/이름 | diary-private |
| 공개 여부 | private (`public=false`), 필수 |
| 파일 최대 크기 | 10,485,760 bytes (10 MiB), 팀 합의 전 후보 |
| 허용 MIME | image/jpeg, image/png |
| 경로 | `{user_id}/{diary_id}/{asset_kind}/{asset_id}.jpg` 또는 `.png` |
| 원본 종류 | original_drawing, 일기당 한 장 |
| 향후 만화 종류 | comic_scene, 장면 번호는 diary_assets.scene_index |

버킷과 파일은 Storage API/Dashboard로 관리한다. SQL에는 버킷 설정용 INSERT/UPDATE나
storage.objects 데이터 조작을 넣지 않는다. [Storage 스키마 공식 지침](https://supabase.com/docs/guides/storage/schema/design)에
따라 서비스 관리 메타데이터를 임의 수정하지 않고, 두 번째 마이그레이션에는 RLS 정책만 둔다.
이름이 같은 기존 버킷이 있으면 공개 여부·기존 데이터·정책부터 검토하고 자동 덮어쓰지 않는다.
버킷을 만들고 정책을 적용하기 전까지 업로드 기능을 열지 않는다.

## 경로와 권한

파일명에는 이름·이메일·아동 발언을 넣지 않는다. BE가 사용자 JWT에서 얻은 회원 UUID와 새 일기/파일
UUID를 이용해 키를 만든다. DB CHECK는 부모 회원/일기/종류/파일 ID/MIME 확장자와 키를 정확히 맞춘다.
Storage 정책은 첫 경로를 `auth.uid()`와 대조하고, UUID 모양의 세그먼트와 허용 종류/확장자만 수용한다.
Storage의 경로 정규식은 UUID 모양 검사이며 나머지 ID의 실재 여부까지 검사하지 않는다.

| 요청 | 일반 회원의 후보 정책 |
| --- | --- |
| SELECT/다운로드/목록/서명 URL 발급 | 본인 접두사만, 원본·만화 허용 |
| INSERT/새 업로드 | 본인 접두사의 original_drawing만 |
| UPDATE/upsert/덮어쓰기/이동 | 차단 |
| DELETE | 차단 |
| anon/익명 로그인/다른 회원 경로 | 차단 |
| 향후 만화 업로드 | 검증된 서버 경로에서만, 사용자 직접 INSERT 차단 |

기본 허용 정책 SELECT/INSERT 2개와 **restrictive** 제한 정책 4개를 둔다.
기존의 넓은 permissive 정책들이 OR로 결합되어도 이 버킷의 소유권·원본만 추가·수정/삭제 차단이
유지되도록 제한 정책이 AND로 적용된다. 다른 버킷은 제한 조건을 통과하며 이 SQL이 새로 접근을
허용하지 않는다. 기존 restrictive 정책은 추가로 차단할 수 있으므로 적용 전 전체 조합을 검토한다.
UPDATE는 기존 행과 변경 후 행 모두 검사하여 다른 버킷으로 빼거나 이 버킷으로 옮기는 것도 막는다.
`storage` 테이블의 기존 권한/RLS를 통째로 회수·변경하지 않는다.

RLS/Storage 관리자와 service_role 등은 이 제한을 우회할 수 있다. 파일은 회원 ID가 포함된
키로 서버가 넣어도 사용자가 읽을 수 있도록 **키로 접근을 판정**한다. service_role 업로드에는
owner_id가 없을 수 있어 그것만 소유권 근거로 사용하지 않는다.
키 생성/다른 회원 경로 금지는 서버에서도 반드시 검사한다.
[공식 Storage 소유권 설명](https://supabase.com/docs/guides/storage/security/ownership)을 참고한다.

비공개 버킷의 파일은 사용자 JWT를 사용한 인증 다운로드 또는 소유권 확인 후 발급한 짧은 만료의
서명 URL로 조회한다. 만료 시간 후보는 5분이며 팀 확인이 필요하다. 서명 URL은 만료 전까지
전달받은 사람이 사용할 수 있으므로 로그/DB에 보존하지 않는다. 공개 URL을 만들거나 버킷을
공개로 바꾸지 않는다. **public=true에서는 파일 제공에 RLS만을 믿을 수 없으므로 비공개 여부가 적용 조건이다.**

## 업로드·원본 보존·실패 처리

1. 후속 BE에서 로그인 회원과 대화 세션/선택 초안의 소유권, 날짜/확인 행위를 검증한다.
   FE가 보내는 user_id, 다른 회원의 session_id, 임의 외부 URL을 신뢰하지 않는다.
2. BE가 일기/원본 UUID를 미리 정하고 실제 파일을 디코딩한다. MIME·확장자·바이트/픽셀 한도를
   검사하고 저장 바이트의 크기·가로세로·SHA-256을 산출한다. 버킷 MIME 제한만으로 실제 이미지임을
   보장하지 않는다. 디코딩 자원 한도, EXIF 개인정보 처리·악성 파일 대응은 후속 구현/합의 대상이다.
3. 본인 경로에 **새 파일로** 업로드한다. `upsert=false`를 사용하며 기존 파일을 지우지 않는다.
   [공식 접근 제어](https://supabase.com/docs/guides/storage/security/access-control)에서 upsert는
   추가 UPDATE 권한을 요구한다. 이번 정책은 원본 덮어쓰기를 허용하지 않는다.
4. 업로드 확인 후 같은 일기 ID로 일기·전체 대화 스냅샷·원본 파일 참조를 하나의 DB 트랜잭션에
   저장한다. 한 트랜잭션으로 묶는 저장 API/RPC는 아직 없으며 별도 REST INSERT 여러 번으로
   원자성을 가정하면 안 된다. 파일 확인 전 done/달력 저장 완료로 표시하지 않는다.
5. 파일 저장 실패 시 DB 확정 저장을 진행하지 않는다. DB 실패 시 업로드된 고아 파일이 생길 수 있다.
   파일/DB는 분산 트랜잭션이 아니므로 저장 요청의 영속 키·지문·진행 상태와 재조회/복구가 필요하다.
   응답 유실·중복 날짜 충돌에서도 기존 저장본을 덮거나 무조건 삭제하지 않는다.
6. 고아 파일은 DB 참조·처리 중 요청·보존 기간을 확인한 **서버의 별도 정리 작업**만 삭제하도록
   추후 설계한다. 이번 초안에는 정리 작업·보존 기간·삭제 권한/RPC를 만들지 않는다.

업로드 선행을 허용하기 때문에 Storage 정책은 diary/asset 행 존재를 요구하지 않는다.
같은 회원의 미참조 파일도 조회/업로드할 수 있다. 타인 접근은 차단하지만 파일 수/총량 제한이나
진위 검증을 대신하지 않는다. 업로드 quota·요청 제한·영속 예약·고아 파일 정리 없이는 비용/복구
문제가 생길 수 있으므로 실제 공개 전 구현해야 한다. 보존 정책 합의 후 예약된 파일만 허용하는
정책으로 강화할지 검토한다.

원본은 **수용한 업로드 파일의 바이트**이며 AI 만화는 별개 키/행이다. 현재 FE가 압축한 JPEG라면
그 이전 canvas의 무손실 데이터를 복원할 수 없다. PNG 채택·형식·해상도·빈 그림 허용은 팀 합의
대상이다. 원본 교체/최종 글 수정/삭제·탈퇴·만화 재생성/실패 결과 보존은 미정이며 현재 일반
회원의 UPDATE/DELETE 금지는 임시 보존 방침이다. 자동 cascade로 파일을 지우지 않는다.

## 적용 전 검증 — 이번 작업에서는 실행하지 않음

- 001과 비공개 버킷 준비 후 002를 적용할 대상 환경을 별도로 확인한다. 정책 생성 권한과
  storage.objects의 기존 RLS/기본 grants, 기존 public/anon/authenticated 정책을 함께 점검한다.
- 가상 회원 A/B로 각자의 원본 업로드·조회 성공과 타인 접두사/위조 이름/만화 업로드 거절을 확인한다.
- 미인증·Supabase 익명 로그인·누락된 is_anonymous claim, 목록/다운로드/서명 URL도 확인한다.
- 덮어쓰기·삭제·버킷 간 이동과 넓은 기존 permissive 정책이 있어도 접근이 거절되는지 검증한다.
- 파일 확장자/MIME/용량 제한, 업로드 성공 후 DB 실패, 커밋 후 응답 유실, 중복 저장 복구와
  원본 해시/이미지 재조회, 서명 URL 만료를 검증한다. 특권 키 테스트만으로 회원 RLS를 검증하지 않는다.
- 실제 DB/Storage 실행과 통합 테스트 전까지 보안 정책이 운영에서 검증되었다고 표시하지 않는다.
