1. 확정된 정책과 이번 구현

정상 확정 일기 1개당 서버가 30코인·1물방울을 결정한다. 별도 시작일 설정 없음.
중복 키는 (member_id, diary_id)다. member_daily_reward_grants라는 기존 후보 테이블 이름은
유지하되 diary_date는 응답/조회용 속성이며 지급의 식별자가 아니다.
기존 diaries_user_date_uq는 변경하지 않는다. 실제 서비스의 하루 한 권 제약은 그대로다.

과거 일기의 소급 여부는 미결정이다. 설치 트랜잭션 안에서 diaries SHARE 잠금 취득 후
그 시점에 존재하는 모든 일기 ID/소유자를 member_reward_legacy_diaries에 기록한다.
이 목록은 지급 기록이 아니며, 지갑/기존 일기/그림을 변경하지 않는다.
기존 일기는 fingerprint 유무와 관계없이 보류한다. 기존 저장 요청 재전송도 보류를 해제하지 않는다.
서비스 역할은 목록 SELECT만 가능하고 일반 회원은 읽기/쓰기 불가다. 자동 삭제/해제 기능 없음.
그 뒤 커밋된 새로운 확정 일기 중 fingerprint가 있는 일기만 지급한다.
새로 저장된 일기의 날짜가 과거/미래여도 지급 대상의 의미는 날짜가 아니라 확정 일기 ID다.
기존 RPC가 실제 서버 확인시각으로 날짜를 정하고 FE 날짜/금액은 받지 않는다.

이 방식은 명시적인 날짜형 정책이 아닌 기존 데이터 보호를 위한 설치 스냅샷이다.
SQL 설치 전 저장된 일기는 모두 보류되므로, 설치와 배포 사이의 범위도 추후 소급 결정 대상이다.
정책 변경 요청 시점과 설치 사이에 작성된 일기에 보상할지는 사용자 결정이 필요하다.
일괄 소급 SQL은 만들거나 실행하지 않았다. 과거 데이터를 설치 뒤 가져오는 복원/수입 작업은
현재 범위가 아니다. 그런 작업은 대상 ID의 보류 등록까지 포함해 별도로 설계해야 한다.
목록을 다시 생성/덮어쓰면 신규 미지급 일기를 보류해 버리므로 재스냅샷도 금지한다.
이 DB 상태를 사용하면 기존 POST /api/me/rewards/sync의 {} 본문을 유지할 수 있다.
DB 상태를 추가하지 않고 {}만으로 신규 확정과 기존 과거 일기를 구별하는 것은 불가능하다.

2. 확정 저장·지급·복구 흐름

기존 POST /api/chat-sessions/{session_id}/diaries의 요청/응답은 변경하지 않았다.
DiaryService.confirm의 메모리 저장, 영속 세션 저장, 기존 요청 복구 세 경로가
_confirmed_detail로 합류한다. 일기 커밋 및 상세 조회 성공 뒤 RoomService.execute(sync_rewards)를
별도 RPC로 호출한다. 보상 실패/timeout/결과 검증 오류는 고정 경고 DIARY_REWARD_SYNC_DEFERRED만
남기고 정상 상세 응답을 유지한다. 키/아동 본문/회원 ID/DB 오류 원문은 로그에 남기지 않는다.
최대 DB 요청 제한시간만큼 응답이 늦어질 수 있다(기본 10초). 백그라운드 큐는 없다.
요청 취소/프로세스 종료는 HTTP 성공 응답을 보장하지 않으나 이미 커밋된 일기는 보존한다.

sync는 회원 확인 → 회원 잠금(seed22) → 지갑행 잠금 → 보류되지 않은 확정 일기 조회 →
지급 기록 INSERT ON CONFLICT DO NOTHING RETURNING → 새 기록 수만큼 지갑 증가를 한 트랜잭션으로 한다.
확정 실패/초안/대화에는 일기행이 없으므로 지급하지 않는다.
일기 저장 커밋과 지급 사이에 재시작하거나 확정 응답을 잃어도 별도 outbox가 필요하지 않다.
영구 일기행 - 보류 목록 - 지급 기록이 복구 대기 목록이다. {} sync 또는 같은 저장 요청 재전송으로 복구한다.
지급 RPC 응답 유실 시 DB에 커밋됐다면 재요청 new_rewards=[]와 현재 지갑을 반환한다.
서버 저장 직후 자동 지급 성공 시에도 이후 FE sync의 new_rewards는 []일 수 있다.
FE는 지갑 응답을 기준으로 잔액을 갱신해야 한다. 기존 JSON 구조/정액 필드는 그대로다.
오프라인 중 앱을 다시 열지 않으면 미지급이 자동 처리된다는 보장은 없다. 필요 시 운영 감시/복구는 별도다.

  - 승인된 BE 배포 후 기존 API 조회/저장 계약을 먼저 확인하고 쓰기를 재개한다.

최소 신규 테스트 계정 검증(실제 기존 회원 잔액 변경 금지):
  - 합의된 전용 신규 회원 T1/T2만 생성한다. 인증메일/외부 발송도 별도 승인 범위에서 한다.
  - T1의 빈 방/{} sync가0인지 확인 → 대화/초안은0 → 정상 확정 뒤30/1.
    같은 저장 요청·새로고침·로그아웃/재로그인·반복 sync·BE 재시작 뒤에도30/1 및 지급1행.
  - 실제 다른 날 두 번째 확정은60/2. 하루 한 권 제약을 풀거나 서버 날짜를 운영에서 조작하지 않는다.
  - T2는 별도 자기 지갑만 읽는다. 상대 일기/보상 조회·직접 잔액/지급/구매/성장 쓰기·RPC 호출이
    회원 JWT/anon에서 거절되는지 실제 권한으로 확인한다. 기존 A/B/C/D sync는 호출하지 않는다.
  - 동시 두 요청의 같은 신규 일기 지급이1회인지, 상품 구매/물 사용 동시 요청이 잔액과 맞는지 확인한다.
    상품 seed는 이 후보에 없다. 승인된 전용 테스트 상품 없으면 구매 경합 검증은 미완료로 남긴다.
  - 장애/응답유실/강제 롤백/락 순서는 운영 전체 권한을 바꿔 재현하지 않는다.
    T 계정 전용 제한된 검증 또는 별도 합의된 환경에서만 실제 다중 연결 검증을 설계한다.
  - 생성503 유지, 기존 일기에 만화 없음/소유권 차단/URL 재발급 확인.
    합의된 실제 생성/연결은 FE·AI 계약과 worker가 준비된 뒤 별도 수행한다.

중단·복구:
  - 잠금 timeout/권한 오류/객체 이름 충돌/기존 자산 변화/잔액 불일치 시 즉시 중단한다.
  - COMMIT 전 실패는 ROLLBACK하고 객체 미생성·기존 수량 보존부터 확인한다.
  - COMMIT 후 문제가 있으면 신규 보상/상점/물주기 경로를 배포/프록시에서 멈추고 이전 BE로 복귀한다.
    보상 호출이 실패해도 기존 확정 저장은 보존하는 코드이며, 무리한 스키마 삭제는 하지 않는다.
  - 후보 객체·보류 목록·지급/구매/물 사용 기록을 보존해 원인을 분석한다. 적용 SQL 전체 재실행 금지.
  - 보상 미지급은 보류되지 않은 신규 일기에 한해 수정 후 같은 {} sync로 복구한다.
    과지급 의심은 실제 회원 지갑 차감/지급기록 삭제로 되돌리지 말고 별도 승인된 보정 계획을 세운다.
  - 보류 목록을 지우거나 신규 스냅샷으로 바꾸지 않는다. 기존 일기에 소급 지급하지 않는다.
  - 사용이 시작된 새 스키마를 DROP하지 않는다. 백업 전체 복원은 이후 저장 일기를 잃을 수 있어
    영향 분석과 별도 승인 없이는 수행하지 않는다. 원본 그림의 객체 삭제/이동/upsert는 금지한다.
